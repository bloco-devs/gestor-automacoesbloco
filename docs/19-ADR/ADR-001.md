## Por que Supabase
- Postgres gerenciado com RLS de primeira classe — casa com nosso modelo de autorização (`has_role`, `is_allowed_user`).
- Auth, Storage, Edge Functions e Realtime no mesmo produto → menos superfícies de operação.
- Migrations versionadas em SQL puro (99 arquivos aditivos) — fácil auditoria e rollback lógico.
- Custo previsível para o volume atual do time interno.
- Alternativas descartadas: Firebase (sem SQL/RLS), backend próprio (custo de operação).

## Por que React + Vite
- Stack padrão Lovable, ecossistema shadcn/ui pronto.
- Vite dá HMR rápido e bundle enxuto.
- TypeScript reduz classes inteiras de bugs de contrato com o Supabase (`types.ts` gerado).
- Alternativas descartadas: Next.js (SSR desnecessário para app interno autenticado), Angular/Vue (fora do padrão do time).

## Por que HUB Bloco ID
- Unifica SSO entre os apps internos Bloco.
- Fornece catálogo vivo do ecossistema, evitando duplicar cadastro em cada app.
- Centraliza consumo de IA — cotas e billing únicos.
- Riscos: dependência forte de disponibilidade → mitigado por fallbacks (IA direta e seed do mapa).

## Por que IA centralizada
- Governança: um único lugar para modelo, prompt, rate limit, telemetria.
- Custo: cotas geridas no HUB.
- Segurança: chaves de LLM não chegam ao cliente.
- Auditabilidade: `ia_uso_log` do lado do app + logs do HUB.
- Consequência aceita: latência ligeiramente maior que chamada direta (compensada pelo fallback).

## Consequências
- Toda função de IA deve passar por `_shared/ia-gateway.ts`.
- Toda tabela nova em `public` deve nascer com RLS + GRANTs.
- Frontend nunca fala diretamente com serviços externos — sempre via edge function ou HUB.
- Dependência operacional dupla: Supabase externo + HUB. Runbooks devem cobrir ambos.
